\chapter{Project Overview}

\section{Project Identity}

The \textbf{Connected Vehicle Intelligence System (CVIS)} is an academic prototype built for the \textit{Computer Communication \& Network Security (CCNS)} course. Its central thesis is that AI reasoning belongs in the cloud, not embedded in each vehicle. The vehicle is a \textit{thin, securely-networked client}; the laptop running the backend acts as the data-centre. CVIS demonstrates the \textbf{secure communication layer} that makes this architecture viable.

\begin{ccnsbox}{Core Thesis}
AI lives centrally (cloud/data-centre). The vehicle is a thin client. The project grades the \textbf{secure communication pipeline}, not the AI itself.
\end{ccnsbox}

\section{Core Objectives}
\begin{enumerate}[leftmargin=1.8cm]
  \item Simulate a realistic EV telemetry pipeline from edge device to centralised server.
  \item Enforce cryptographic integrity (HMAC-SHA256) and optional confidentiality (AES-256-GCM) on every packet.
  \item Demonstrate runtime protocol switching between HTTP REST and MQTT publish-subscribe without restarting any service.
  \item Provide a live Network Operations Center (NOC) dashboard that visualises packet flow, security events, and chaos simulations in real time.
  \item Integrate Ollama AI reasoning over multi-factor telemetry to produce contextually accurate driver recommendations.
\end{enumerate}

\section{Non-Goals}
\begin{itemize}
  \item Real EV hardware or real sensors — telemetry is simulated on an ESP32 or via the Python physics engine.
  \item A generic chatbot with no telemetry grounding.
  \item Three separate frontend codebases (one unified Next.js app serves all three roles).
\end{itemize}

\section{MQTT Topic Taxonomy \& Control Loop}

In addition to inbound telemetry streaming, the MQTT communication layer coordinates bidirectional configuration and node revocation:

\begin{itemize}
  \item \texttt{cvis/telemetry/\{device\_id\}}: Uplink topic for vehicle telemetry envelopes (plaintext or AES-256-GCM encrypted).
  \item \texttt{cvis/config/protocol}: Downlink broadcast topic where the backend announces runtime transport shifts (\texttt{"http"} vs \texttt{"mqtt"}). Subscribed firmware nodes switch protocols on receipt without power cycling.
  \item \texttt{cvis/config/encryption}: Downlink broadcast topic toggling AES-256-GCM encryption mode on or off.
  \item \texttt{cvis/config/control/\{device\_id\}}: Unicast node control channel. When the NOC deactivates a node, a \texttt{"disconnect"} message is published to this topic. Subscribed vehicle firmware immediately transitions into an idling suspended state, halting all radio transmissions until a \texttt{"reconnect"} instruction is received.
\end{itemize}

On resource-constrained microcontrollers (ESP8266/ESP32), JSON memory buffers are strictly calibrated to \texttt{StaticJsonDocument<1024>} to ensure full 17-parameter multi-factor telemetry frames deserialize without memory exhaustion or silent key dropping.

\section{Device Registration Flow}

When the Python simulator or an ESP32 first connects:

\begin{enumerate}
  \item \texttt{POST /api/v1/devices/register} with \texttt{\{"device\_id": "SIM-001"\}}.
  \item Backend generates: \texttt{api\_key = secrets.token\_hex(32)} and \texttt{device\_secret = secrets.token\_hex(32)}.
  \item \texttt{api\_key\_hash = SHA256(api\_key)} is stored in \texttt{devices} table. The plaintext \texttt{api\_key} is returned once.
  \item All subsequent requests include \texttt{X-API-Key: <plaintext>} and \texttt{X-HMAC-Signature: <hex>}.
\end{enumerate}

\section{HMAC-SHA256 Implementation}

HMAC is computed over the \textit{exact raw JSON bytes} as transmitted. This is critical: even a single extra space in the JSON would change the HMAC and trigger rejection.

\begin{lstlisting}[language=Python, caption=HMAC Computation (backend/crypto.py)]
def compute_hmac(secret_hex: str, payload: str) -> str:
    key = bytes.fromhex(secret_hex)        # 32-byte (256-bit) key
    sig = hmac.new(key, payload.encode("utf-8"), hashlib.sha256)
    return sig.hexdigest()                 # 64-char lowercase hex

def verify_hmac(secret_hex: str, payload: str, signature_hex: str) -> bool:
    expected = compute_hmac(secret_hex, payload)
    # hmac.compare_digest prevents timing-oracle attacks
    return hmac.compare_digest(expected, signature_hex.strip().lower())
\end{lstlisting}

\section{AES-256-GCM Encryption}

\begin{lstlisting}[language=Python, caption=AES-GCM Encrypt/Decrypt (backend/crypto.py)]
def aes_gcm_encrypt(secret_hex: str, plaintext: str) -> dict:
    key    = bytes.fromhex(secret_hex)   # 32 bytes = 256-bit AES key
    aesgcm = AESGCM(key)
    nonce  = os.urandom(12)              # 96-bit random nonce per message
    ct_with_tag = aesgcm.encrypt(nonce, plaintext.encode("utf-8"), None)
    ct  = ct_with_tag[:-16]             # ciphertext bytes
    tag = ct_with_tag[-16:]             # 128-bit GCM authentication tag
    return {"iv": nonce.hex(), "ct": ct.hex(), "tag": tag.hex()}
\end{lstlisting}

The GCM \textbf{authentication tag} doubles as an integrity check: decrypting with a mismatched key or tampered ciphertext raises \texttt{InvalidTag}, which the backend logs as a \texttt{tamper\_detected} event.

\section{Remote Node Revocation \& Session Management}

To emulate real-world vehicular certificate and session revocation without tearing down underlying TCP sockets, CVIS implements centralized node deactivation:

\begin{enumerate}
  \item \textbf{Revocation Trigger}: An operator at the NOC issues a disconnect command (\texttt{POST} \nolinkurl{/api/v1/control/disconnect}).
  \item \textbf{Database State Transition}: The backend sets \texttt{devices.active = 0} and records an audit entry in \texttt{auth\_logs} under event type \texttt{disconnected}.
  \item \textbf{Protocol-Specific Enforcement}:
    \begin{itemize}
      \item \textit{HTTP}: Subsequent telemetry requests from the revoked device are rejected with HTTP 401 (\textit{Unauthorized}) at the API key authentication gate.
      \item \textit{MQTT}: A downlink revocation signal is published to \nolinkurl{cvis/config/control/{device_id}}. The firmware halts telemetry loop transmissions, preventing broker congestion.
    \end{itemize}
  \item \textbf{Re-activation}: When connectivity is re-authorized (\texttt{POST} \nolinkurl{/api/v1/control/reconnect}), the device's active flag is restored, a \texttt{reconnected} audit log is generated, and resume instructions are dispatched to the node.
\end{enumerate}

\section{Open vs. Secured Traffic Auditing}

For academic and demonstration purposes, authentication enforcement can be toggled live via the NOC (\texttt{POST /api/v1/config/auth}). When disabled, incoming frames without valid API keys or HMAC signatures are accepted rather than dropped. However, to maintain strict security auditing:
\begin{itemize}
  \item Packets are saved to SQLite with \texttt{auth\_status = 'no\_auth'} rather than \texttt{'ok'}.
  \item A dedicated entry is written to \texttt{auth\_logs} indicating unauthenticated access.
  \item The WebSocket broadcast flags the packet with \texttt{status = 'ok'} and \texttt{auth\_status = 'no\_auth'}, enabling the NOC packet inspector to highlight open traffic clearly.
\end{itemize}

Vehicle identities are segmented into distinct capability tiers:

\section{Physics Model Overview}

The simulator is a \textbf{stateful physics engine}. Each tick (every 2 seconds) computes the next state based on the current state. No values are hardcoded per mode; modes are \textit{emergent} from the physics.

\subsection{Load Factor Computation}

The \textbf{Load Factor} ($L$) is the normalised measure of how hard the vehicle is working at any instant:

\begin{equation}
L = \underbrace{\frac{v}{50}}_{\text{speed drag}} + \underbrace{\frac{(v + w)^2}{10000}}_{\text{aerodynamic drag}} + \underbrace{g \cdot 0.5}_{\text{gravity drag}} + \underbrace{\max\!\left(0,\; \frac{36 - p_t}{10}\right)}_{\text{tire drag}}
\label{eq:load}
\end{equation}

where $v$ = speed (km/h), $w$ = headwind (km/h), $g$ = road gradient (\%), $p_t$ = tire pressure (PSI).

\subsection{Battery Drain Model}

\begin{equation}
\Delta \text{SoC} = \left(L \cdot 0.1 + \frac{P_{\text{cabin}}}{5000}\right) \cdot \Delta t
\label{eq:drain}
\end{equation}

\subsection{Thermal Model}

\textbf{Motor Temperature:}
\begin{equation}
\Delta T_{\text{motor}} = (L \cdot 2.0 - (T_{\text{motor}} - T_{\text{ambient}}) \cdot 0.05) \cdot \Delta t
\label{eq:motor-temp}
\end{equation}

\textbf{Battery Temperature:}
\begin{equation}
\Delta T_{\text{battery}} = (\Delta \text{SoC} \cdot 5.0 - (T_{\text{battery}} - T_{\text{ambient}}) \cdot 0.02) \cdot \Delta t
\label{eq:batt-temp}
\end{equation}

\subsection{Range Estimation}

\begin{equation}
r = \text{SoC} \times 3.0 \times f_{\text{tire}} \times f_{\text{wind}} \times f_{\text{cabin}}
\label{eq:range}
\end{equation}

where penalty factors are: $f_{\text{tire}} = 0.9$ if $p_t < 32\;\text{PSI}$; $f_{\text{wind}} = 0.85$ if $w > 20\;\text{km/h}$; $f_{\text{cabin}} = 0.95$ if $P_{\text{cabin}} > 1000\;\text{W}$.

\section{Prompt Engineering}

The prompt is built in \texttt{backend/ai/prompt\_builder.py}. The user message sent to Ollama contains:

\begin{enumerate}
  \item \textbf{Current Snapshot}: all 17 telemetry fields from the latest packet.
  \item \textbf{Advanced Physics Section}: ambient temp, headwind, road gradient, tire pressure, cabin load, cell voltage delta — labelled \texttt{=== ADVANCED PHYSICS ===}.
  \item \textbf{Trend Block}: last 5 readings rendered as a sparkline text table (battery \%, speed, motor temp, mode).
  \item \textbf{Range Violations}: any field that has crossed its warning threshold.
  \item \textbf{Mode Transition}: previous mode is explicitly shown when a mode change is detected.

The system prompt instructs the model to: (1) classify severity as \texttt{NORMAL} / \texttt{CAUTION} / \texttt{WARNING} / \texttt{CRITICAL}, (2) reason from the \textit{combination} of factors rather than any single threshold, and (3) output exactly two lines: severity label + recommendation.

\section{AI Throttling}

To prevent LLM overload, the background AI task fires only when:
\begin{itemize}
  \item At least 20 seconds have elapsed since the last inference, \textbf{OR}
  \item The vehicle mode has changed since the last packet.
\end{itemize}

\section{Concurrency Serialization \& Event Loop Safety}

High-frequency telemetry ingests across multi-vehicle fleets can trigger simultaneous inference requests to the local Ollama daemon. Without concurrency bounding, parallel execution of 3B parameter models on consumer hardware causes severe memory contention and latency spikes.

In \texttt{backend/ai/ollama\_client.py}, inferences are strictly serialized through an asynchronous lock. To prevent the notorious Python \texttt{RuntimeError: Task attached to a different loop} issue—which occurs when an \texttt{asyncio.Lock} is instantiated at module import time before FastAPI initializes its runtime event loop—CVIS employs a thread-safe lazy factory:

\begin{lstlisting}[language=Python, caption=Lazy Event-Loop Lock Factory (backend/ai/ollama\_client.py)]
_ollama_lock: Optional[asyncio.Lock] = None

def _get_ollama_lock() -> asyncio.Lock:
    global _ollama_lock
    if _ollama_lock is None:
        _ollama_lock = asyncio.Lock()
    return _ollama_lock
\end{lstlisting}

Every inference invocation in \nolinkurl{generate_recommendation()} and \nolinkurl{chat_with_grounding()} executes inside \texttt{async with \_get\_ollama\_lock():}, guaranteeing sequential model execution bound safely to the active running loop.

\section{Hierarchical Kill-Switch \& Graceful Service Degradation}

CVIS enforces a two-tiered administrative kill-switch hierarchy:
\begin{enumerate}
  \item \textbf{Global Service Switch} (\texttt{server\_config.ai\_service\_enabled}): Toggled via \texttt{POST} \nolinkurl{/api/v1/control/ai-service}. When disabled by NOC operators, all automated background inferences and conversational AI queries across the entire fleet are instantly halted.
  \item \textbf{Per-Vehicle Gating} (\texttt{vehicle\_ai\_enabled}): Toggled via \texttt{POST} \nolinkurl{/api/v1/control/ai-service/vehicle}. Allows operators to selectively disable AI reasoning for individual vehicles (e.g., degraded nodes or billing holds). The global kill-switch maintains strict precedence over per-vehicle settings.
\end{enumerate}

When AI is toggled off or if the local Ollama process is unresponsive, the system gracefully degrades: the background pipeline suppresses inference without dropping telemetry, and the driver chat endpoint (\texttt{POST} \nolinkurl{/api/v1/ai/chat}) immediately returns an HTTP \texttt{503 Service Unavailable} status with an explicit status payload:
\begin{lstlisting}[caption=HTTP 503 AI Degradation Response]
{
  "status": "disabled",
  "detail": "AI service is currently disabled by administrator."
}
\end{lstlisting}
The frontend detects this HTTP 503 code and renders an unobtrusive service pause badge rather than spinning indefinitely.

\section{The ``Driver Intuition'' Fallacy}

A frequent industry objection to connected vehicle AI systems is the \textit{Driver Intuition Fallacy}:
\begin{quote}
\textit{``Why should an operator pay for centralized AI when an experienced driver intuitively knows that high speeds and steep hills drain the battery and heat up the motor?''}
\end{quote}

While human intuition is capable of learning crude, qualitative heuristics (e.g., ``driving faster drains the battery''), human cognition possesses severe and fatal limitations in modern electric vehicles:

\begin{enumerate}[leftmargin=1.5cm]
  \item \textbf{Reactive vs. Predictive Anomaly Detection}: Human drivers react exclusively to dashboard warning indicators, which illuminate only \textit{after} a critical threshold is breached (e.g., Battery Temp $> 60^\circ\text{C}$ or Motor Temp $> 95^\circ\text{C}$). At this point, irreversible cell degradation or forced vehicle immobilization has already begun. CVIS utilizes \textbf{Sliding-Window Trend Analysis} across consecutive telemetry packets to compute rate-of-change derivatives ($\Delta T / \Delta t$). The cloud AI detects thermal gradient anomalies rising $1.5^\circ\text{C}/\text{min}$ faster than expected under current load, alerting the operator up to 15 minutes \textit{before} any hardware threshold is tripped.

  \item \textbf{Coupled Multi-Variate Physics vs. Gut Feeling}: EV range and thermal behavior are governed by non-linear coupled differential equations combining aerodynamics, road gradient, tire pressure, HVAC auxiliary draw, and cell internal resistance. If a driver asks:
  \begin{center}
  \textit{``I have 24\% battery remaining, ambient temperature is $38^\circ\text{C}$, headwind is $35\text{ km/h}$, and I need to climb a $6\%$ grade in stop-and-go traffic for $18\text{ km}$ with air conditioning active---will I reach the destination?''}
  \end{center}
  Human intuition is mathematically incapable of answering this. CVIS acts as a real-time \textbf{Conversational Physics Simulator}, integrating all 17 live telemetry values against validated physical load models to provide a mathematically bounded, high-confidence guidance response.

  \item \textbf{Fleet-Wide Swarm Intelligence}: An individual driver is isolated within their own vehicle envelope. Centralized AI aggregates telemetry across thousands of deployed nodes in real time. If 20 vehicles along a specific highway corridor experience anomalous battery heating or localized rolling-resistance spikes due to extreme ambient heat or road conditions, the central AI immediately flags predictive alerts to all upstream vehicles entering that corridor.
\end{enumerate}

\subsection{Eliminating Parasitic Battery Drain and Thermal Overhead}

Electric vehicle range anxiety remains a decisive consumer barrier. In-car edge AI computers impose a severe, continuous parasitic electrical load:
\begin{itemize}[leftmargin=1.5cm]
  \item \textbf{Continuous Power Draw}: Running multi-billion parameter neural networks locally on automotive chips consumes \textbf{70W to 250W} of continuous high-voltage power.
  \item \textbf{Thermal System Congestion}: On hot summer days ($35^\circ\text{C}$--$45^\circ\text{C}$ ambient), the Battery Thermal Management System (BTMS) is already operating near capacity cooling the traction battery and inverter. Adding a 200W heat source to the coolant circuit forces the A/C compressor to cycle harder, accelerating range degradation.
  \item \textbf{Phantom Sentry Loss}: In parked standby mode, an edge computer drawing 150W consumes \textbf{3.6 kWh per day}---resulting in \textbf{20 to 30 km (12--18 miles) of battery range lost every 24 hours} without moving.
  \item \textbf{The CVIS Advantage}: In CVIS, the vehicle's telemetry gateway draws under \textbf{1.5 Watts}. All heavy matrix multiplications and language synthesis occur in cloud data centers powered by industrial electrical grids. The vehicle's high-voltage pack is preserved exclusively for motion and climate control.
\end{itemize}

  \item If cell \#42 in a battery module exhibits a subtle voltage delta during high-rate fast charging, the local computer has no statistical baseline to determine whether this represents normal cell aging or an imminent thermal runaway hazard.

In the \textbf{CVIS Centralized Cloud Model}:

  \item Telemetry from millions of deployed vehicles streams into a central high-speed ingest database (\texttt{packets} and \texttt{telemetry}).
  \item Cloud analytics execute \textbf{Cross-Fleet Anomaly Clustering}:
  \begin{itemize}

\section{Cloud vs. On-Vehicle Edge AI: Architectural Lifecycle Comparison}

\subsection{Zero-Downtime Model Deployment vs. Risky Automotive ECU OTA Flashing}

Automotive Over-the-Air (OTA) firmware updates are notoriously high-risk, expensive, and logistically fragile:
\begin{itemize}[leftmargin=1.5cm]
  \item \textbf{The Edge AI Dilemma}: Updating a local model weights file (e.g., 3GB to 8GB) requires broadcasting multi-gigabyte files to hundreds of thousands of cars over cellular 4G/5G connections. Automakers pay millions in telecom carrier data egress fees. The driver must park the car for 30--60 minutes. If power cuts or flash memory corrupts mid-flash, the vehicle ECU is \textbf{bricked}, requiring dealer towing. Furthermore, flashing safety ECUs requires lengthy regulatory homologation re-certification.
  \item \textbf{The CVIS Cloud Paradigm}: Model upgrades occur \textbf{100\% in the data center} via dynamic model hot-swapping (\texttt{POST /api/v1/ai/models/switch}) or blue-green container deployments. Upgrading from \texttt{llama3.2:3b} to \texttt{llama3.3:8b} or \texttt{qwen3:8b} takes \textbf{under 30 seconds}. There is \textbf{zero vehicle downtime}, \textbf{zero cellular OTA download risk}, and \textbf{instant 1-second rollback} if regressions appear.
\end{itemize}

\subsection{Hardware Longevity and Automotive Lifespan Mismatch}

The operational lifespan of a modern passenger vehicle is \textbf{12 to 15 years}.
\begin{itemize}[leftmargin=1.5cm]
  \item \textbf{The Edge Silicon Trap}: If an automaker integrates an AI processor in 2024, by 2028 that chip is four hardware generations obsolete. It lacks the TOPS, memory bandwidth, and quantization support to run 2030 foundation models. Within five years, the vehicle's onboard assistant feels sluggish and abandoned.
  \item \textbf{The CVIS Future-Proof Guarantee}: Because reasoning lives in the cloud, a 10-year-old vehicle built in 2024 continues to receive state-of-the-art multi-factor intelligence in 2034. When the data center upgrades its GPU clusters from RTX 4060s to Blackwell or optical AI silicon, every vehicle in the fleet immediately inherits that compute capability.
\end{itemize}

\section{Scripted Engineering Defense Dialogues}

\subsection{Dialogue 1: The ``Why Not an In-Car Chip?'' Challenge}
\begin{dialoguebox}{Examiner Interaction: Edge Silicon vs. Cloud AI}
\textbf{Examiner:} \textit{``Why shouldn't automakers just put a powerful AI chip inside the car? Silicon gets cheaper every year.''}

\textbf{Candidate Defense:} 
\textit{``That sounds attractive in theory, but in real automotive manufacturing it encounters the \textbf{Automotive Hardware Lifespan Mismatch}. An electric vehicle is engineered to remain operational for 12 to 15 years. AI algorithms and model architectures, however, evolve every 12 to 18 months. If an automaker puts an AI chip in a car in 2024, by 2028 that chip is already obsolete---it cannot run the larger reasoning models or newer attention mechanisms of the future.}

\textit{Furthermore, in automotive grade electronics (AEC-Q100 / ISO 26262), silicon qualification takes 3 years before production, meaning the chip in a brand new car is already 3 years old on day one! By making the car a thin, securely-networked client and placing the AI centrally, the automaker can upgrade their data center GPUs from RTX 4060s to H100s or Blackwell tomorrow, and a 10-year-old vehicle in the field instantly inherits state-of-the-art intelligence without requiring a physical recall, an expensive chip replacement, or risking a bricked ECU over an OTA flash.''}
\end{dialoguebox}

\subsection{Dialogue 2: The ``What If the Internet Disconnects?'' Challenge}
\begin{dialoguebox}{Examiner Interaction: Network Outages and Safety}
\textbf{Examiner:} \textit{``What happens when the car enters an underground parking lot or a remote highway with zero cellular service? Does the car stop working?''}

\textbf{Candidate Defense:} 
\textit{``Absolutely not. In CVIS, we maintain a strict architectural separation between \textbf{Real-Time Vehicle Safety Controls} and \textbf{Supervisory AI Intelligence}. The physical actuators---braking, steering, traction control, motor inverter control---run on hard real-time local microcontrollers over isolated CAN buses. The AI in CVIS is strictly an advisory, predictive, and analytical layer.}

\textit{To guarantee continuous operation during network blackouts, CVIS incorporates a local pre-warmed multi-factor intelligence engine (\texttt{ai\_cache.py}). If cellular connectivity drops, the gateway falls back to this deterministic cache in under 5 milliseconds, providing accurate safety advice and mode recommendations based on live physics rules until the network restores. Simultaneously, telemetry is buffered locally in flash and uploaded upon reconnection. The car never stops, and the driver is never left without guidance.''}
\end{dialoguebox}

\subsection{Dialogue 3: The ``Driver Intuition'' Challenge}
\begin{dialoguebox}{Examiner Interaction: Human Intuition vs. AI Physics Simulation}
\textbf{Examiner:} \textit{``Why do we need an AI at all? Doesn't a driver already know that driving fast in cold weather reduces range?''}

\textbf{Candidate Defense:} 
\textit{``A human driver has basic qualitative intuition, but human intuition cannot solve non-linear multi-variate differential calculus while driving at 100 km/h. For example: If a driver has 22\% battery, ambient temperature is -2$^\circ\text{C}$, cabin heater is drawing 2.5 kW, headwind is 25 km/h, and they face a 6\% uphill gradient over the next 15 km in heavy traffic---will they make it to the charger?}

\textit{Human intuition will guess and risk stranding the vehicle. The CVIS multi-factor AI reasons over all 17 telemetry parameters simultaneously: battery cell delta, internal resistance, motor thermal rise rate, and aerodynamic draw. It computes an exact, mathematically grounded power trajectory and advises the driver: `Reduce cabin heat to 1 kW and cap cruising speed at 85 km/h to arrive at the charger with 4\% reserve.' That is predictive precision that human intuition cannot match.''}
\end{dialoguebox}

\section{Tamper Detection Sequence}

When \textbf{tamper injection} is enabled and \textbf{auth is enabled}:

\begin{enumerate}
  \item ESP32 sends JSON with HMAC over the \textit{original} payload.
  \item ChaosMiddleware changes \texttt{battery\_pct: 999.9} in the body.
  \item \texttt{auth.py} reads the (now mutated) body and recomputes HMAC.
  \item HMAC mismatch detected → \texttt{tamper\_detected} event logged to \texttt{auth\_logs}.
  \item Backend returns \texttt{HTTP 401} with \texttt{"HMAC signature verification failed"}.
  \item NOC packet table shows \texttt{auth\_status = tamper\_detected} in red.
\end{enumerate}

\section{CCNS Technical Examination: Questions \& Authoritative Answers}

\subsection{Unit 1: Data Communication \& Application Layer Protocols}

\paragraph{Q1: Why was JSON selected as the primary telemetry payload serialization format?}
JSON provides a human-readable, self-describing, and schema-agnostic serialization format natively supported across Python, JavaScript, and embedded C/C++ (via ArduinoJson). Crucially, JSON accommodates an explicit \texttt{schema\_version} field (e.g., \texttt{"1.0"}), enabling backward-compatible protocol evolution without breaking existing parser contracts. In CVIS, incoming payloads are validated at the FastAPI gateway boundary using strict Pydantic schemas that enforce field types, physical ranges, and mandatory cryptographic signatures.

\paragraph{Q2: How does the adaptive telemetry transmission interval function, and what network principles does it demonstrate?}
Rather than transmitting at a static rate, the vehicle gateway dynamically alters its transmission frequency based on the active operational mode:
\begin{itemize}[leftmargin=*,nosep]
  \item \textbf{Safety-Critical Modes} (\textit{Battery Overheating}, \textit{Motor Fault}): Transmission interval accelerates to \textbf{1 second}.
  \item \textbf{Routine Cruise Modes} (\textit{Healthy}, \textit{Eco}): Transmission interval throttles down to \textbf{5 to 8 seconds}.
\end{itemize}
This directly implements the principles of \textbf{Differentiated Services (DiffServ)} and \textbf{Priority Queuing} (CCNS Unit 1). In bandwidth-constrained cellular environments, safety telemetry is prioritized, cutting routine cellular data volume by 70\%+ while ensuring sub-second response times during thermal runaway emergencies.

\paragraph{Q3: Is the simulated telemetry engine composed of random numbers, or does it follow physical dynamics?}
It is a \textbf{Continuous Stateful Physics Engine}. Both the embedded firmware and the Python digital twin maintain internal state variables across loop cycles ($\Delta t$). Energy drain follows aerodynamic drag ($P \propto v^3$) and road rolling resistance. Incline gradients impose gravity loads, while motor and battery temperatures rise via coupled differential heat equations ($dT/dt = k_{\text{in}} P - k_{\text{cool}} (T - T_{\text{amb}})$). When switching to Sport Mode, acceleration spools up smoothly, battery SoC drops faster, and thermal gradients spike realistically, feeding the AI mathematically valid multi-factor dynamics.

\subsection{Unit 2: Network Models \& Transport Protocols (HTTP vs. MQTT vs. WebSocket)}

\paragraph{Q4: What are the fundamental transport differences between HTTP REST and MQTT in CVIS, and when is each preferred?}
\begin{itemize}[leftmargin=*,nosep]
  \item \textbf{HTTP REST} (Request-Response over TCP): Client initiates every transaction, server returns an HTTP response, and connection closes or enters keep-alive. Each POST incurs $\approx 800\text{ bytes}$ of HTTP header overhead. It is ideal for point-to-point, low-frequency telemetry with mandatory synchronous receipt acknowledgements.
  \item \textbf{MQTT} (Publish-Subscribe over Broker): Client maintains a single persistent TCP socket to an MQTT broker, exchanging compact 2-byte fixed topic headers. It supports hierarchical routing (\texttt{cvis/telemetry/\{id\}}), wildcard subscriptions (\texttt{+}), and configurable Quality of Service (QoS 0/1). It is vastly superior for high-frequency, massive-fleet IoT streaming.
\end{itemize}
CVIS provides a \textbf{runtime protocol switch}: the NOC can transition the active fleet between HTTP and MQTT instantly without restarting any client or server daemon.

\paragraph{Q5: How does the WebSocket architecture differ from traditional REST polling for dashboard observability?}
REST polling requires each frontend tab to issue periodic requests (e.g., \texttt{GET /api/v1/telemetry/recent} every 2 seconds). This introduces up to 2,000 ms of artificial display latency and floods the server with redundant requests when state is unchanged. CVIS establishes a single, persistent \textbf{full-duplex WebSocket connection} (\texttt{/ws}) using HTTP protocol upgrade (RFC 6455). When an ingest packet arrives, FastAPI's \texttt{ConnectionManager} fans out the event in under 1 ms to all active views (\texttt{/driver}, \texttt{/noc}, \texttt{/admin}) simultaneously.

\subsection{Unit 3: Transport Layer Reliability \& Chaos Engineering Middleware}

\paragraph{Q6: How does the application-layer retry mechanism mirror transport-layer TCP retransmissions?}
While TCP handles retransmissions invisibly at the kernel transport layer, mobile cellular networks often drop application-level HTTP/MQTT requests due to gateway timeouts or transient packet drops. CVIS implements application-layer exponential backoff: if a POST fails to receive HTTP 200 within a timeout window, the client retries with intervals of 1s, 2s, and 4s. This is directly analogous to \textbf{Karn's algorithm} in TCP, doubling retransmission timeouts to avoid exacerbating network congestion.

\paragraph{Q7: Why is chaos testing (packet loss, latency injection) implemented as ASGI middleware rather than kernel netem?}
Linux kernel shaping (\texttt{tc netem}) requires root access and does not operate on loopback localhost traffic. CVIS implements \texttt{ChaosMiddleware} directly in the Python ASGI pipeline. When packet loss is set to 25\%, the middleware intercepts the raw request before FastAPI route dispatch, draws a pseudo-random float, and returns HTTP 503 Service Unavailable probabilistically. When latency is configured to 300 ms, \texttt{asyncio.sleep(0.3)} yields control to the event loop. From the vehicle's perspective, RTT increases identically to real physical propagation delay.

\paragraph{Q8: How does CVIS ensure that slow AI model inference does not block incoming vehicle telemetry?}
AI inference (averaging 150ms to 400ms on CUDA GPUs, and up to 8s on CPU) is completely decoupled from the telemetry ingest pipeline. FastAPI launches the inference coroutine via \texttt{asyncio.create\_task()} as an asynchronous, non-blocking background job. The HTTP handler returns \texttt{200 OK} to the vehicle in under 4 ms, immediately writing the telemetry packet to SQLite and broadcasting the raw data over WebSockets. When the AI finishes its multi-factor analysis, it broadcasts a secondary \texttt{ai\_recommendation} event downstream.

\subsection{Unit 4: Cryptographic Wire Security \& Integrity}

\paragraph{Q9: How does HMAC-SHA256 provide message integrity without encryption, and how does AES-256-GCM differ?}
\begin{itemize}[leftmargin=*,nosep]
  \item \textbf{HMAC-SHA256} generates a 32-byte cryptographic hash using a shared device secret: $\text{HMAC}(K, M)$. It provides \textbf{authenticity and integrity}, guaranteeing the packet originated from the genuine vehicle and was not modified in transit. However, the payload is plaintext (no confidentiality).
  \item \textbf{AES-256-GCM} is an Authenticated Encryption with Associated Data (AEAD) cipher. In a single cryptographic pass, it provides \textbf{confidentiality} (AES counter mode encryption) and \textbf{integrity} (Galois Message Authentication Code GMAC tag). The packet is completely opaque on the wire.
\end{itemize}

\paragraph{Q10: What is a timing oracle side-channel attack, and how is it eliminated in CVIS?}
In naive string comparison (\texttt{hash1 == hash2}), the processor terminates comparison at the very first mismatched byte. An attacker intercepting network packets can measure execution latency with microsecond precision, deducing correct signature bytes one by one. CVIS strictly employs Python's \texttt{hmac.compare\_digest()}, which executes in \textbf{constant time} regardless of mismatch position, completely eliminating timing leakage.

\paragraph{Q11: How does replay attack protection operate in CVIS?}
Each telemetry payload includes a monotonic boot-relative timestamp millisecond token (\texttt{timestamp\_ms}). The backend maintains an in-memory sliding cache of observed \texttt{(device\_id, timestamp\_ms)} tuples within a 30-second rolling window. If an attacker captures a valid signed packet and resubmits it, the backend identifies the duplicate token and immediately rejects the packet with HTTP 401 Unauthorized.
